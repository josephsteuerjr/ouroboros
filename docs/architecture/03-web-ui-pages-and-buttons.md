# 3. Web UI Pages & Buttons

One build-free SPA serves every surface — desktop shell, browser, Docker, Telegram mini app, phone and the Linux fallback — and this chapter maps its pages (Chat and Projects, Files, Skills and Widgets, Dashboard, Settings and onboarding), the frontend contracts they share (navigation, appearance, notifications, dialogs, primitives, host bridges) and how each page projects runtime truth. The decision that shapes every section: the browser paints facts the host stamps (row placement, outcome phase, receipts, liveness census) and derives none of them from text, timing or a client-side list.

### SPA shape and host bridges

The Web UI is a build-free vanilla-JavaScript SPA (`web/index.html`, shared CSS, `web/modules/*`): no TypeScript or bundler, so the running interface stays inspectable and editable by Ouroboros without opaque build artifacts. `web/app.js` owns top-level page, Project-panel and mobile-navigation state; feature modules own their presentation; every long-lived UI acquisition carries a disposer bound to the lifecycle that created it (DEVELOPMENT "UI resources carry a disposer"). The Linux browser fallback changes presentation only — same API, onboarding contract, runtime identity and state owner — and the browser stays the owner's application outside process custody (§1). One shared WebSocket serves the whole application, Projects open no sockets of their own, and REST is the recovery and durable-read path (§4 WebSocket protocol).

The desktop shell exposes `MainApi` (`window.pywebview.api`, `launcher.py`): native confirmations (runtime mode, reviewed-skill auto-grant, skill key grant); the alert and shell half inherited from `launcher_background.DesktopApi` — `request_attention`/`notify_owner`, `shell_info`, `request_native_notifications`, `show_native_notification` (`desktop_notifications.py`); and the file and URL helpers `download_file_to_downloads`, `open_file_with_default_app`, `open_external_url`, `save_bytes_to_downloads`. Loopback-file methods accept only the server's own host and port and paths under `/api/files/download`, `/api/extensions/...` and `/api/tasks/...`. The packaged launcher changes only on reinstall while the frontend updates with the managed repo, so `ui_helpers.js` feature-detects every bridge method per call and uses file-helper fallbacks or copy-link-plus-toast when one is missing; its link interceptor serves both top-level documents, the SPA and the framed onboarding wizard (`OnboardingHostApi`). The Telegram proxy's `X-Ouroboros-Telegram-MiniApp: 1` marker makes `server_web.make_index_page` include the Telegram SDK; it is presentation only and grants no authentication authority.

### Navigation and shared UI contracts

Appearance is client-local, not a runtime setting; same-origin windows share the stored choice. `web/theme.js` runs before CSS in both first-party documents; `ouroboros.theme` stores `light`, `dark` or `system`, `data-theme-choice` keeps the choice and `data-theme` the palette resolved through `prefers-color-scheme`. `[data-theme-control]` is one shared radiogroup mounted by Settings → Appearance and the onboarding document; it owns no `s-` input, so the Settings collector never posts it, and `ouro:theme-changed` fires only on a resolved palette change. `theme_palette.js` re-tints mounted Charts in place.

`web/modules/notifications.js` is the one notification owner: classification and a delivery gate over one live frame, with client-local preferences (`ouroboros.notifications`, kept like the theme choice, so Settings never posts them). `attach()` takes one subscription per client on the shared socket in `app.js` (`chat`, `quiz`, `log`); `chat.js` has no notification code, because a chat instance dies with its room and a closed Project must still pull the owner back. Only live frames reach it, never history or reconnect backfill, so replay safety is structural rather than a stored ledger. The room gate mirrors `chat_activity.mainThreadAccepts`, so an external owner transport notifies while the hidden partition and A2A ids never do. Categories and importance come from lifecycle facts and the existing `system_type` discriminator, never from text. Delivery prefers desktop system notifications, with browser or in-app fallback; policy and limits: DESIGN §9; rule: DEVELOPMENT "notifications ring for live events only".

Independent iframe documents inherit neither the host's tokens nor its stored choice; a module declares its intent in `render.appearance` (`host`, `independent`, `fixed`; advisory — CREATING_SKILLS). Every first-party `webview.start(private_mode=False)` (`launcher.py`, `launcher_onboarding.py`) requests persistent website storage, because pywebview's default private mode erases the WebView's website data whenever a window opens. In-app updates replace only the core, so a packaged launcher built without that flag keeps erasing until reinstalled; `desktop_shell.js` discloses such an app in Settings → Appearance from `shell_info()` or the launcher-stamped `/api/health` `app_version`.

Primary navigation exposes Chat (Main), a collapsible Projects group, Files, Skills, Widgets, Dashboard and Settings; About is a Settings sub-tab. `syncNavigationState()` is the single presentation state machine for active page, active Project, Projects expansion, mobile drawer and panel backdrop, so independent toggles cannot leave two rows active or a hidden surface looking selected. Sidebar and panel widths are owner-local preferences, not runtime settings. The application has one client-side route: a `#<page>` fragment honoured once on load, validated against an existing `#page-<name>` section and never written back, because the desktop shell and the Linux fallback have no address bar and the Telegram mini app always loads at `/`. Projects are panels, not routes; the sidebar is the document's one `<nav>` landmark.

Each active or deleting Project has a sidebar row with pointer- and keyboard-operable open, rename and delete; the backend owns the name limit (`PROJECT_NAME_MAX`) and lifecycle truth. Unread Projects sort first, then by durable activity; a deleting Project is non-openable until the server publishes registry state. On narrow screens navigation is an explicit drawer and the Project chat a full-width overlay; no gesture-only layer competes with scroll, selection or the software keyboard.

`confirm_dialog.js::openConfirmDialog` owns browser dialogs: confirm returns a strict boolean, input `{confirmed, value}` (empty on cancellation), alert one acknowledgement; Cancel, Close, backdrop, Escape and supersession never confirm, and critical controls test the exact confirmed result. Native `window.prompt`/`confirm`/`alert` are forbidden: shells render them inconsistently, they block the event loop, and PyWebView's prompt fails silently. ### Chat and Projects

#### Timeline ownership and ordering

`web/modules/chat.js` owns the canonical message timeline, drafts, attachment staging, runtime controls, budget projection, routing annotations, task and child cards, WebSocket subscriptions, thread routing, insertion order, unread state and reconnect reconciliation; `chat_media.js` (per instance) owns delivered-media presentation and the composer's paste and drop targets, and `chat_attachments.js` owns staged files and the owner's attachment block. Every ordinary message has one canonical durable chat row; Project views are lenses over those rows and task bindings, so conversion creates no second message, unread event or cost record. Routing acknowledgements live in a sidecar keyed by `client_message_id` and update the existing owner message without a synthetic assistant bubble; the open-or-focus action appears only when the confirmed destination differs from the viewing chat.

Messages, media bubbles and task-card roots order by raw numeric timestamps (ties keep arrival order; the typing indicator stays last). Band anatomy and the `Reviews N` count: `docs/DESIGN.md`.

History reconciliation is one synchronous transaction over keyed records that preserves timeline and Review nodes, disclosure, focus and selection; a child keeps one keyed lifecycle row across live delivery and replay, older pages cannot regress it, and a task's current result outranks its historical terminal observation. `LIVE_CARD_CAP` bounds live accumulation: past it a fresh history read is requested and only completed, unrepresented cards captured before it may leave the view.

`chat_history.js` bounds rendered pages with `maxPages`, retaining reading, focus and selection protection; `historyCoverage` is proof of byte delivery — EOF, shared IDs, chronology and `canNewer` prove nothing, and an unhealed gap stays partial. `chat_reading_position.js` owns the viewport: it follows explicit live-edge intent near the bottom, otherwise keeps the reader's anchor; every room opens on its newest message through `showLatest` (the ↓ path), and only an archive-edge gesture reads older pages. `createHistoryControls` owns the edge button and the header's loading, gap, error and approximation status; `Load more history` (DESIGN "History edges") retries a failed read, else reads older pages while any exist. Origin adoption uses `project_dialogue.project_origin_identity`.

#### Main rows and host-stamped card rows

DESIGN's role/type and `_emit_progress.narration` survive `send_with_budget` and replay; Host Service accepts exact-origin terminal replies in either voice. Progress callbacks capture address, lineage and attempt at binding, so a late review cannot inherit another turn; unkeyed progress and summary rows never mutate a live card.

`terminal_projection.py` owes the Project row and the deferred Main mirror together. `write_task_result` stamps `canonical_terminal_projection_origin=terminal_transition` only on an accepted root terminal transition, never from an incoming write, projector or replica, so markerless historical rows are never replayed. Readiness precedes effects: publication and retirement require `headless.terminal_task_files_ready`, because synthesis alone does not prove artifact completion. Retirement requires durable Main registration or proven ineligibility, with matching token, attempt, checkpoint and artifact facts. Publication errors are isolated from task-done and retried at checkpoint, startup and the `server_maintenance.py` sweep. The bounded outbox and at-least-once transport preclude exactly-once.

Main receives its own dialogue, Project quiz mirrors and `project_dialogue.MAIN_PINNED_ROW_TYPES` (`project_handoff`, `project_started`, `project_completion_summary`, and a root's `main_notice` from `send_user_message(destination="main")`), pinned at supervisor send and `room_membership` replay; other Project traffic stays in its room. Lifecycle `text` is plain: producers strip markdown before persistence. `projects_registry.mirrored_answer` carries the whole `completion_answer` only for a nonempty `model_final` in a settled phase within `MIRRORED_ANSWER_MAX_CHARS`; otherwise it is absent, never cut; `project_answer.js::decorateProjectRow` adds the fold and the reference (DESIGN "Project completion mirror"). `ORIGIN_ADDRESSED_NOTICE_TYPES` (`task_not_started`, `task_start_unconfirmed`, `steer_not_delivered`) stay in their issuing chat on replay despite target binding.

Every unanswered Project quiz is mirrored into Main from one keyed pointer, without a second durable message; `chat_decision.buildQuizCard` renders the same Project form plus the Project reference (DESIGN "Project question mirror") over the existing decision ingress. The first confirmed `answered` observation from any source starts one `MIRROR_SETTLE_MS` countdown that later observations never restart; only Main's copy retires, Project history remains. Lifecycle moves forward only: a settled question never reopens within an instance, and a stale snapshot cannot revive a removed copy. Once the bounded `OBSERVATION_LIMIT` memory has forgotten a question, it mounts as safe unknown and reads canonical task detail; unavailable or wrong-project detail leaves "Status unavailable", the Project reference and no answer controls.

`project_dialogue.project_question_pointer`, live `message_bus.send_quiz` and the census `required_question` carry the same question fields; a narrower redelivery never blanks a known field. `question_presentation.js` owns the lifecycle wording; `project_dialogue.QUESTION_STATUS` is its Python twin, pinned by `question_presentation_parity.json`. Waiting requires positive evidence, and history carries the same wait facts because ordinary input can resume a task without a `quiz_state` frame. `appendActivityQuestion` ends only demonstrably older waits of the same task — a strictly earlier `asked_at` proves order; request time, equal rounded timestamps and missing stamps do not — and never settles a question. An answer HTTP response must contain a valid recorded answer; a malformed confirmation never substitutes the local draft.

A host fact about a task is a row of that task's card, never a standalone bubble beside it: the producer stamps `card_row` (`timeline` or `reviews`) and `card_row_id` (stable across live delivery, outbox replay and history) and the browser attaches the row to the task's card record as one timeline item (`reviews` also refreshes the card's Reviews group). Only a row whose task has no card record in the page renders as a standalone System row with the same words; the untyped terminal host notice and the origin-addressed notices carry no placement fact and stay ordinary rows by design.

Finality metadata is row-specific. Durable `task_summary` rows carry the same phase the browser paints: `project_dialogue.outcome_phase` mirrors `log_events.js` and is stamped as `outcome_phase` beside the status word from `OUTCOME_PHASE_HEADLINE`, so there is no second status-word family. The pre-finalization authored row carries the phase with `outcome_final=false` but no host verdict clause; only terminal `task_summary` rows append the host verdict clause (`_completion_verdict`) when one exists. The Main `project_completion_summary` puts the shared headline and any verdict in its plain text and carries no `outcome_phase`; its optional `completion_answer` is the mirrored answer, not a finality fact. The start row carries neither outcome finality nor a verdict. A verdict is one owner sentence from `project_dialogue.TASK_CAUSE_PHRASES`, keyed by the typed reason code (a code without a sentence stays raw): the execution reason, or, when the host's acceptance decision is anything but accepted, the decision's reason; the stored reviewer rationale stays on the task result and in Logs, and the verdict leads the Main completion row, so a host-authored row never presents an unaccepted claim as the whole story.

#### Project handoff receipts

`project_handoff.py` owes one Main transfer receipt (`project_handoff`) through the terminal outbox after the durable bind, keyed by `handoff_id` = captured ingress message plus Project, so a technical retry shares its receipt and independent requests never merge. The answer is one typed word (`RECEIPT_STATES`), never a boolean, because binding and receipt durability are separate facts: `durable`/`already_delivered` prove the Main row is owed or delivered; `origin_unproven` (no recorded Main message) writes no receipt, because Main is never a default; the other words name a transport or binding gap. The supervisor handlers for the agent's promote and scope events (`supervisor/events_project_routing.py`) discard the word; their gaps surface only through the outbox's typed event and warning log. `POST /api/projects/from-task` returns `handoff_receipt` and `handoff_id`; `chat.js` speaks a non-durable word as a warning on the card (`data-receipt`), never as history.

`project_handoff.js` (Main only) keeps one visible receipt per identity without hiding cards: it folds under the first converted card or receipt, folding a durable receipt clears the card's not-saved mark, and reconciliation is node-scoped so replay stays linear. The census owns the phase; without one, a single-flight detail read per episode, terminal wins. Main-origin direct turns moved into a Project get ordinary completion mirrors; Project-native turns stay in their room.

#### Composer, attachments and delivered media

The Main composer exposes one-shot Swarm planning, the owner Nano/Low/Max context choice, file attachment and Send. Swarm places a structural `force_plan` fact on the next ordinary message and disarms after that send; it is never inferred from keywords. The host admits one managed root in the sending room without a model call, carrying the verbatim owner objective, origin, surface and attachments; the root may choose its Project through `ensure_project_scope` (§6 In-task project scoping). Nano/Low/Max uses the dedicated owner endpoint: a derived Low fit never masquerades as an owner-selected posture, and the choice sizes Ouroboros's own working window, never review authority. Project panels omit global Restart, Panic, evolution, consciousness, review and budget controls, which belong to the one Ouroboros process, not a Project thread.

Attachments stage via paperclip, paste or drag-and-drop with no count or size rejection; staging is local, upload begins on Send, and offline handling is the WebSocket queue contract (§4). Structured attachment metadata lets the gateway expose a native image to a vision-capable route and stage the complete file set through the shared artifact substrate.

Simple text messages may appear immediately as pending local bubbles that reconcile against their echoed `client_message_id`. Owner attachments (DESIGN "Chat attachments"): the canonical writer claims the frame's uploads in the ingress critical section and records server-measured refs on the row; upload response, echo and history carry the same `chat_uploads.attachment_view`. Delivered documents capture immutable task-owned bytes and carry a verified `file_ref` plus canonical download URL, rebuilding from history without persisting base64; `download_url_compat` serves only the host bridge's Open and Download. Files above the inline boundary (`core_artifacts._MAX_DOCUMENT_FILE_BYTES`) are file-backed; photos and videos keep base64 only in the live frame, and supported media is stored under the canonical task artifact root with a content-addressed URL so replay restores the same bubble. Structured `links` rows render at most `MAX_LINK_ACTIONS` independently revalidated HTTP(S) buttons. The supervisor transport owns durable media copies so all producers converge on the canonical data root; failed persistence stays an honest caption row and cannot finalize a task card.

#### Direct turns and the activity block

Ordinary Main and Project conversations use complete native execution even while other work runs: each turn owns its agent and creates no supervisor queue record. The process-local `supervisor.active_activity.DirectActivityRegistry` retains the private actor handle from preparation through result delivery; Stop, Hurry, quiz and steering resolve that exact actor, while `active_direct_turns` and typing frames expose presentation fields only. The managed-update writer drain waits for registered executions, custody maintenance and the restart census include their IDs, and the consciousness alarm clock starts no wake while an owner direct turn is live.

`_is_direct_chat` is one fact carried by the durable result, the terminal event, the rebuilt `task_done`, the authored `task_summary` row, the history terminal-truth annotation (`gateway/history.py`) and the census `kind`, so a late or replayed Project completion stays in its room without a Main summary and a block reads the same truth live, on reload and on reconnect. Every worker progress frame carries the typed `narration` fact (`ouroboros/agent.py::_emit_progress`): `True` only for the model's own words — the round narration from `loop_messages.py::_emit_round_progress` and a tool relaying the mind's recorded reason verbatim (`plan_review._narrate_author_rationale`) — and `False` for every host note (checkpoint, model fallback, review verdict). `gateway/history.py::_PROGRESS_META_FIELDS` whitelists it into history, so only narration reaches the card title and collapsed activity line while a host note stays a visible timeline row; a frame without the fact is read as narration.

`chat.js::blockVisible` reevaluates content, open attention and work at every mutation (predicate: DESIGN "Conversation activity block"). Successful tool calls fold into one `chat_activity.js::toolEvidenceView` row (`tools|<task>`); failures keep their own counted rows, and host metrics replace live call facts. `blockHasWork` decides task-card chrome, direct or managed; `_is_direct_chat` drives only the client header pill.

Addressing calls carry host `routing_action` frames and `routing_tool_calls` metrics from `tool_capabilities.ROUTING_VERBS`; their receipt is the annotation on the owner message. Completion acts carry `completion_control` and `completion_tool_calls`. These receipt rows render inside an existing block but never create one; failures remain content, `tool_calls` still counts every call, and live, reload and reconnect use these facts without a client tool-name list. A refused addressing act states the host's `cause` verbatim through `routingAnnotationText`; "Choose a target" requires real options. A host-issued act refused before starting adds one `📋 System` row (`task_not_started` / `task_start_unconfirmed`) keyed to the never-started task; replay neither creates nor finishes its card.

#### Liveness census and the chat header

`GET /api/state` combines direct turns and managed root tasks in `active_chat_activities` with the frozen status vocabulary (§11.1 What is frozen); parked direct turns keep their ID and `kind="direct_chat"`, and `pause_cause` names budget, owner, restart, sleep or unknown without granting execution. Only the census inserts live entries; finals and census delete them. Absent IDs clear only with `active_chat_activities_complete === true` and `supervisor_ready === true`, whatever the kind; an incomplete read retains positives, and completeness requires every live-identity source. One shared `/api/state` sequencer (`chat_activity.js::createStateSnapshotSequencer`): the Main chat polls it on a short interval while the Chat page is open and `app.js` on a longer one on every page; at most one read is in flight, and forced refreshes coalesce into one follow-up.

Typing is a submission receipt: it matches `client_message_id`, retires the local `Sending...` bubble and requests a census; it never inserts, revives or extends liveness. The header reducer reads connection, census, unconfirmed owner sends and live managed cards; a direct block is not a managed card, so the header keeps the census verdict while a mounted unfinished block hosts its running indicator, and terminal failure remains a task result, never a reasonless header `Attention`. A typed `ingress_accepted` echo adds `Input saved`, carried by the canonical inbound row into history and reload without implying task admission. Only the reducer writes the badge: idle is `Starting…` until `supervisor_ready` is true (re-proven per reconnect), then `Online`.

`web/modules/project_activity.js` groups census rows by `project_id`, minus unbound, child and duplicate rows; wait rows pass the chat card's `mergeModelWaits` admission. Partial positives stay current; omissions, errors, disconnect and an unreadable question detail (`required_question_unavailable`) stay static unknown, and only a complete supervisor-ready snapshot clears an absence.

Owner rows and routing annotations stay in the bounded local journal until history returns their `client_message_id`. Early root answers carry `task_phase="finalizing"`, also derived on replay from the open checkpoint; `task_cost_finalized` never closes a card. `log_events.taskTerminalSummary` projects settled task-scope status as `observedOutcome`: the outcome owns the chip and `task_phase_chip.setLiveCardPhaseSecondary` adds a quieter `Finalizing…`.

Two invariants close the class of liveness the server cannot name: typing-fed header phantoms and cards shielded by a client-held live set. First, the history window is lineage-closed (`ouroboros/gateway/history.py`): subagent lineage older than the window's recency floor is kept only while the child runs or finalizes, its parent is represented by the response (a row proving its card; typed photo, document and quiz deliveries do not count) or the parent is alive; an anchored child represents its own children, so a nested swarm is kept or dropped whole, and a final row failing that test is emitted without lineage fields, so replay cannot mint an unfinishable parent card. Second, liveness reconciles over the card set, not only the census: only an id the census actually lists shields a card; an unvouched connected root card is finished only by proven durable terminal detail; a card without a current result stays unconfirmed until a complete fresh snapshot excludes it, then uses the retained typed terminal fact or a neutral `Outcome unavailable` anchor without phase or controls. A root proven terminal settles descendant cards a lost child terminal left open from each child's own durable result, never by cascade from the parent's outcome; until then such a child keeps a `Working` chip without live dots.

#### Task cards, errors and reason lines

`log_events.js` keeps the live task card and grouped task cards on one reducer in Chat and Dashboard Logs. Nonterminal LLM, tool and checkpoint failures stay in details without promotion; only authoritative task truth changes terminal status, and unknown Chat names gain no severity from keywords. `task_checkpoints.js` owns the typed checkpoint vocabulary (`log_events.taskCheckpointLabel`); unknown kinds name themselves, and only a kindless positive `checkpoint_number` proves a periodic self-check. Checkpoints and `context_reclaim` appear in the expanded card, never as titles, collapsed narration or toasts. Global workers stay in Logs (`worker_starting`, `worker_ready_window_extended`).

`categorizeLogEvent` uses `summarizeLogEvent`'s phase for Errors. Replayed `tools.jsonl` uses the same typed facts (`ok`/`level` outrank names); a call's start row is its live frame, read as `Started <tool>`, never liveness. Keyword matching remains only the non-expanding fallback for untyped unknown Logs events. A `swarm_fanout` with `role="delegated_run"` names a delegated run, not a child. Failed children keep local `Failed` while their root continues. Cards show a plain latest-activity line and an expandable timeline; truncated rows fetch full typed results. Cards navigate results, never own them. Only explicit `task_incident` facts raise urgent toasts.

`taskReasonDetail` joins recorded causes once with ` · `: a soft stop adds none, a hard failure names the execution reason, and a cancellation names its source and flattened cause. Only `request_origin.kind="agent_task"` identifies an actor; `requested_by` alone cannot. Lineage supplies parent/ancestor wording without IDs; cancel_task uses the asker's relation (`cancel_presentation.cancelCauseClauses`, Python twin `supervisor.cancel_publication.cancel_cause_clauses`). Non-accepted acceptance uses cause-table text without status or rationale; a blocking plan uses the objective reason. Deferred children (`outcome_axes.objective.deferred_count`), open review (`terminal_plan_review_open`) and custody debt stay beside the cause. Unknown codes stay raw; Logs also names review and acceptance status.

#### Child cards and executor presentation

Subagents render as child cards keyed by their child task ids; a parent holds lineage references and never duplicates the child's final answer. Nested children collapse by default, the chip carries status, and Agent model or Coordinator is labelled in metadata beside the executor observation (layout: DESIGN "Conversation activity block"). A harness pin the resolution refused shows `{harness} · blocked` beside the typed `subagent_executor_unavailable` terminal, never `dispatched` or `no run yet`. Reviews are not lineage: a reviewer run's receipt lives inside the owning task card and mints no child. Selected `subagent_id`, requested route, effective engine route/model/account and terminal execution evidence stay separate facts, so intent is never redrawn as proof of where the run settled.

`executor_observation` (emitted by `delegate_progress.py` from already-polled run detail; envelope: §11) keeps requested and observed provenance apart; `execution_evidence` and `actual_substrate` are settlement-only; `harness_presentation.js::executorIdentityMarkup` is the one renderer of Coordinator, Agent model and observed-model identity. `delegated_activity.js` projects executor speech, thinking, problems and technical counts inside root and child cards, live and on replay — speech leads, thinking folds, problems stay visible, source links address the retained redacted JSONL (§6 Delegated activity). Host observations confer no narration, title or terminal proof.

#### Reviews projection

The task card's `Reviews` section is a read-only projection over independent domain authorities — skill review history, typed plan-review state, task-acceptance evidence, repository-review records — each keeping its own lifecycle, verdict and enforcement. A row needs a stable review identity, a real presentation-owner task, typed domain state and, where required, exact subject binding; the admitted rows are task-bound Skill Review, plan review and task acceptance, while advisory and commit review stay on their domain surfaces. The projection synthesizes no task-wide verdict and changes no routing, status, attention or enforcement; there is no review inbox, generic review endpoint, review ledger or second state machine. Task-result `plan_review_state` stays the plan-review authority. A `review_reference` row is addressed to the task's bound Project chat, else the chat its caller named, else the hidden partition: Main is never its default, and `chat_id=0` remains the hidden Skill Review partition. When review history is the only retained fact for an owner, Chat renders an inert owner anchor with `Reviews` and no task phase or liveness. Opening and closing Reviews belongs to the user (DESIGN "Reviews inside task cards"; renderer `review_presentation.js`).

#### Card cost

A card's cost is one scope's accounting facts (amount, finality, subtree, reservation, unknown) bound by `cost_presentation`, never a per-call `cost_usd` alone (producer: §6 Budget tracking; words: DESIGN "Conversation activity block"). Root-tree evidence outranks own scope; no attributable subtree rows means absent, not zero. Dashboard and task detail read the ledger, not cards; compact Reviews carry no money, while exact-job Skill Review detail reads it from the ledger. Precedence and the live-root feed: `cost_projection.py`.

#### Stop and cancel controls

Cancel appears only on unfinished, unconverted root cards whose host attests `cancelable=true`; card shape grants no control, and native direct tasks follow §5 custody. The shared dropdown sends `cascade:true`: hard stop waits for teardown or refusal, Wrap up records durable finalize intent and returns 202 pending. Completion wins, a missing live task reconciles from durable state, and unproven death stays a visible refusal. Reason lines: `log_events.taskReasonDetail` over `cancel_origin` (§3 Task cards, errors and reason lines).

#### Turning a card into a Project

A Main managed or Swarm root card becomes a Project in one click. Conversion creates the Project or adopts the one the task's owner message already has (`adopted: true`; toast `Project opened`, else `Project created`), binds the task and its origin message, moves live work onto the Project lane and swaps the Main action for a Project pointer. A fresh conversion also binds the origin's live sibling roots and direct turns (`project_origin_siblings_bound` in `events.jsonl`), to avoid duplicate Projects for one owner message; an adopting conversion binds only the clicked card, and `task_bindings` in `/api/state` marks the message's other live tasks `origin_bound` — their button closes and their pointer opens the Project while their cards stay in their chat. A request naming a different `project_id` is an explicit choice and keeps the 409. No button on tasks already bound, on children (they inherit their root's Project by lineage) or on blocks that have done no work; a direct-turn card is convertible, its durable bind is its commit point, and its later rows route to the Project room per event. Mechanism: §6 Project binding by task and by origin.

The Project reference (`project_reference.js`; DESIGN "References and actions") appears only on Main root cards and opens or focuses the panel, never closes it; the client has no naming authority. Project-scoped is not project-bound: a headless/CLI run carries a `project_id` for lease and memory without a durable binding — addressed to the Project thread at admission (§5), it never mints a Main card and needs no conversion button.

#### Project rooms

A Project chat's status bar carries one navigation pointer (`project_work_pointer.js`) to the latest unfinished non-child card, else the latest root; it creates no card or execution state and never selects the next message's recipient (labels: DESIGN "Project work pointer").

The New Project dialog takes exactly one source: no folder, a fresh managed genesis workspace, an attached existing folder or a cloned Git URL. Attach uses a server-side directory browser so the flow works in web and Docker; Git-specific operations require a Git worktree. Every folder source discloses that Project tasks get read, write and shell access there; provenance is a durable historical fact, not recomputed from current git state (`project_create.js`).

Deleting a Project is lifecycle work, not filesystem deletion (§6 Project registry and lease): the server fences new admission, cancels and quiesces the Project task subtree, then tombstones the registry entry; the UI may say deletion started but never claims completion early. Project id, canonical history, task bindings, memory, provenance and the working folder remain — deleting the row is not permission to erase the owner's repository or the agent's history.

Project unread is `visible_revision > project_seen_revision` (DESIGN "Project unread dot"): standalone messages advance it, a child's media and questions included; card rows and progress do not. `project_read_state.js` acknowledges a revision after a covering history read paints in the visible room with the newest message in view; the server clamps and max-merges ACKs (`gateway/ui_preferences.py`).

`app.js` keeps at most one live Project chat instance and destroys it on close or switch; the one exception is client state the server cannot rebuild — staged `File`s or an upload in flight — whose instance is hidden, reused on reopen and destroyed once its work settles. Unsent text survives in per-thread session storage; hidden rooms accumulate no listeners and acknowledge nothing (DEVELOPMENT "UI resources carry a disposer").

#### History reads and the SSE v2 transport

Task events (progress, chat, events, tools, supervisor) read retained archive chains and live files. Interactive Chat history (`GET /api/chat/history`) pages a room in its own rows, not in bytes of the shared chain, so a Project's newest messages stay reachable however far back they sit; a Project read skips closed archives whose cached summary (`gateway/history_segments.py`) rules the room out. An opaque additive `cursor` selects older ranges, `has_more` follows the conversation while narration pages alongside, and changed room membership returns `history_view_changed`, never a mixed view. `window.complete` means complete reachable history, independent of `has_more`; additive `coverage` v1 reports per-source delivered spans, witnesses and gaps. One mapper in `history.py` serves recent and older pages alike (mechanism: `history_paging.py`, `history.py`).

Lineage discovery, task-list ordering and Main's newest-result selection share `task_result_facts.py`'s stat-invalidated memo (§1); `history_gap` frames with `lineage_incomplete` are nonfatal diagnostics that consume no history rank.

`POST /api/tasks/{id}/events` is the read-only SSE v2 transport (`TaskEventsRequest`, checked by `validate_ingress` before cursor semantics): JSON `{v:2, wait, cursor}`, the cursor holding one byte offset per root/source across the complete archive-plus-live chain. Events follow physical root/source order, never timestamp ranks, because ranks mis-order retroactive inserts across reconnects; each row carries a stable `event_id` and the cursor after that row. Frames: `cursor_replay` on a filter change, `cursor_checkpoint` at wait expiry (skipped bytes advance, no progress claimed), `history_gap` for an immutable malformed line, `cursor_unavailable` for an unreadable required segment or a shorter chain, never a reset. The offset guarantee needs archives immutable and retained; only an explicit creation fact (`created_at` stamped before preparation) may skip older archives, and skipped bytes still count. A result-directory failure is an explicit error, never an empty view. The GET form and `iter_task_events` keep timestamp-sorted integer ranks; the CLI uses POST and falls back to GET only on a first-connection HTTP 405 (buffering, pass pinning, dedupe: `gateway/task_events.py`, `cli.py`). The agent-facing `chat_history` tool reads the same live-plus-rotated timeline with provider, account, conversation, thread, actor and date filters.

History adds an inert `task_evidence` carrier for represented or addressed tasks, in the task's own room only — a notice Main pins for a Project task mints no carrier and no card in Main. It spends no conversation quota and supplies no row identity or liveness, yet keeps the whole terminal truth: when it is the task's only terminal row in the window, reload settles the card from it. Quiz-bound `owner_wait` facts project independently of Project question details, so Main and Project waits end on the same recorded answer; confirmed pauses leave task-keyed System rows through `pause_notices` (§5).

### Files

Files is a full gateway-backed file manager, not a chat attachment picker: navigation, preview (image, sandboxed PDF, text with an explicit binary/unsupported state), editing, create, upload, download, open in the OS, copy, move, paste and recursive delete; the desktop host bridge and the web fallback share one download contract. Save exists only for a writable complete text read — a truncated preview stays read-only — and unsaved text is guarded on selection, directory change, navigation and unload. The backend is the path authority (root confinement and symlink policy: §4); UI path strings and disabled buttons are presentation only.

### Skills and Widgets

Skills has three views: installed, ClawHub and OuroborosHub. The installed view merges extension truth with the serialized lifecycle queue, so queued and running install, update, review, dependency work, enable/disable, repair, uninstall and failure stay visible. A failed primary read keeps a labelled previous list or an unavailable state, never an empty success; hub facts on installed rows are `null` until the catalog read lands, so the installed list never waits for the hub; Hub Updates and Use Hub version confirm before any POST (`skills.js`).

Installation, deterministic preflight, LLM review, owner grants, dependency readiness, extension loading, enablement and execution are separate lifecycle facts: a fresh review implies neither granted keys nor installed dependencies, and `enabled=true` does not override a blocked review or a load error. Owner attestation skips only the expensive LLM review; preflight and reconciliation still run. Repair and run is an ordinary managed task entered through owner-message ingress; a later direct owner disable wins over it, and automatic repair carries no enable authority. Hub publication uses the selected-skill preflight and an ordinary managed task; the passive Installed projection neither runs Betterleaks nor claims publication readiness.

#### Widgets page

Widgets is a separate page because extension UI is an execution surface, not catalogue metadata. It renders only the UI tabs of reviewed live extensions from the passive projection `GET /api/widgets` (a card's `revision` is the owning skill's `content_hash`, a change signature, not an ETag; Skills stays on `/api/extensions`). Cards reconcile by key on a visible `extension_lifecycle` event, on every WebSocket (re)connect and from the Retry of a failed read; an unchanged card is never remounted, and a changed one is stopped before its replacement mounts. There is no list polling and no global Refresh, because retrying discovery must never stop a kept-running program behind the owner's back; a failed read keeps the last good cards, and `WIDGET_REQUEST_TIMEOUT_MS` bounds the list and preferences reads (`widget_list.js`, `widget_job.js`).

The framed render modes share one capability set — `sandbox="allow-scripts allow-pointer-lock allow-downloads"`, `allow="autoplay; fullscreen; clipboard-write"`, never `allow-same-origin` (author contract: `docs/CREATING_SKILLS.md`). A route iframe (`kind: iframe`) is the skill's own page with no bridge and declares the `route` it loads; a route-less registration is accepted but paints a not-supported card. A declarative widget is rendered by host-owned code from a validated schema. A module widget runs in an opaque-origin `srcdoc` iframe under a CSP that `web/modules/widget_module.js` builds from the page origin (`default-src 'none'`, no `connect-src`); height bounds and geometry keys: `extension_ui_validation.py`. Card order, widths (`widget_size`) and the per-card launch-policy override (`widget_start_mode`) are host UI state in `/api/ui/preferences`; `masonry.js` packs cards through `--masonry-*` custom properties alone, so a reorder or resize never moves a node or reloads a frame (DESIGN "Widgets board").

Framed cards start under a launch policy — the owner's override over the author's `render.start` over the kind default (module and route iframe `manual`, declarative `auto`; `widget_card.js`) — with one Start/Stop control. `retain` keeps a framed card mounted while Widgets is hidden and ends it on Stop, when its skill leaves the live list, on a changed `revision` and with the window, never on the server's word alone. A module widget is stopped in order with acknowledgement (`ouro-widget-disposed`, else `WIDGET_DISPOSE_ACK_TIMEOUT_MS`), one mount in flight per card key; a route iframe disposes synchronously. Chart.js is bundled locally, so rendering never depends on a third-party CDN. Engineering rules: DEVELOPMENT "Embedded surfaces declare geometry and refresh semantics", "UI resources carry a disposer", "Declarative widgets".

#### Declarative widgets

Declarative widgets cover forms and actions, status, data, text, code, markdown, tables, tabs, charts, polls, jobs, streams, subscriptions, progress, media, files, maps, calendars and kanban, composed through `group`, `metric` and `callout`; one recursive validator bounds the tree and reports the exact failing path (limits and identity: `docs/CREATING_SKILLS.md`). Within one mount, data updates reconcile nodes in place, preserving input identity, selection and live password text. `subscription.render` stays transitively passive, so an incoming event cannot smuggle a new active control tree past validation; text, attributes, links, media routes and field values are escaped or constrained for their actual sink.

#### Module widget bridge

A module widget receives one parent-mediated I/O bridge on a per-mount nonce (`widget_frame.js`) — the frame's only scriptable network path, since `connect-src` is closed — so reviewed skill JavaScript keeps useful route I/O without the SPA's cookies, DOM or broad API authority. `OuroborosWidget.fetch` relays only to the owning `/api/extensions/<skill>/...` prefix with same-origin credentials and redirect refusal; WS events arrive through `onEvent` filtered by `ws_prefix`; external links go through the host bridge; an opted-in module subscribes to the resolved theme through `onTheme`, and the parent injects no palette or theme-setting authority. The module endpoint serves only live reviewed registration text, and its opaque-origin response carries `Access-Control-Allow-Origin: *`. Script and CSP faults and content-height reports travel on the same nonce into the card status.

#### Author UI kit

Optional author controls reuse the installed `web/ui.css` and `modules/ui_primitives.js` rather than a second declarative renderer: `server_web.read_author_kit_assets()` reads them through the serving-root resolver and creates no endpoint, cache or state; recipes: `docs/examples/author_ui_kit/`. Authors may override or omit the kit; a failed kit load stays inside the author application.

#### Out-of-process extension responses

An out-of-process extension response streams through `extension_route_stream.py`: process and bundle contexts live across asynchronous startup and teardown, blocking work runs off the ASGI loop, and `runtime_limits.py` owns the chunk and cleanup bounds, which are not response deadlines (extension runtime: §13).

### Dashboard

Dashboard groups Logs, Evolution, Costs, Updates and Activity under the common tab binder; each sub-tab owns its loading and refresh policy instead of running every expensive reader while hidden. Charting uses the bundled Chart.js (§3 Widgets page).

Logs merges live WebSocket log frames with bounded REST backfill from the events, tools, progress and supervisor logs: chronological order, dedupe across live and reconnect overlap, bounded grouped task cards, raw record on demand, and the shared category/severity/review presentation of `log_events.js`. A failed backfill names the unavailable sources in a separate status row while live events continue; clearing the panel deletes no log.

`project_admission_hold` (a gateway contract field) carries the host's label, reason and detail, not a phase; mounted unfinished children read `/api/tasks?queue_only=1` on chat refresh. A missing or unreadable queue never proves recovery; same-id recovery clears the hold, and parked phases, Stop and terminal outrank it. Main keeps the `Paused · …` prefix, Activity the cause and controls (`chat_activity.js`).

Activity joins queue entries with the same refresh's `/api/state` census; a partial census cannot prove idleness, and an unavailable queue never renders empty. Independent sections show the consciousness alarm and schedules; a failed read keeps the others. Authoritative controls are cascade cancellation, consciousness start/stop and schedule enable/disable/delete/restore; every schedule button sends action and reason to the audited `POST /api/schedules/{id}/action`, never a stale record rewrite (`activity.js`).

Costs is a projection of the physical-attempt ledger distinguishing confirmed, reserved, unresolved upper-bound, unknown/unmetered usage, open rows and finality; unavailable data renders as unavailable, not `$0`. Breakdowns by model, key, model category and task category are views over the same ledger. Total budget hot-applies; the per-task value is a hard cap over the whole root tree of the next task, not an own-task soft warning (§7 Default settings), and raising a cap does not resume work that already finalized or paused.

Evolution shows the evolution state, the consciousness alarm clock, campaign objective and progress, queue/failure/budget information and durable history; starting a campaign uses the shared input dialog, where confirmed empty input selects the backend's default autonomous objective. Light runtime mode disables self-modifying campaigns rather than offering a control the backend will refuse.

#### Updates

Updates separates passive status from explicit mutation. Opening the page reads cached local update and git state without touching the network, carrying the last real check's timestamp and a minimal `update_tx` projection so a re-opened panel sees an assisted resolution in progress. One pure verdict (`updates.js::updateVerdict`) renders one primary action whose label is the real next continuation, from Check for updates to Restart now; "Up to date" is claimed only over an actual check result, and a failed check keeps its actionable label. Apply confirms before acting and names the path: a clean update restarts the server, a conflicting one starts the reviewed assisted task (model spend disclosed) whose progress lands in chat. The served-SHA decision is the only page-reload authority; the boot-owned `pending_boot_smoke` and `applying_replace` phases keep the synthetic `restarting` state until a post-reconnect `update_status_ready` proves boot finalization returned. Recovery holds "Save recovery point" (moves only this installation's local `ouroboros-stable` fallback, never the official QA feed — §8) and one restore list labelled by local tags; unavailable, divergent, dirty, unsafe, failed-check, rollback and restart-required are states, not extra buttons. Passive Git reads take no optional index lock, so they cannot contend with the update writer.

The Markdown `letter` reuses the status payload and `update_status_ready` without another poll; Refresh calls `/api/update/check`. `server_process.capture_server_source_baseline` pins the startup source before any mutation, so the letter tells the server baseline from the caller checkout — landing is not adoption, and unknown never becomes disk HEAD (`update_letter.py`). The lock-owning apply executor publishes stage observations through `gateway/update_progress.py` into the status payload (`update_progress`): real stages without percentages or timers, never an authority for mutation or recovery.

### Settings and onboarding

Settings has Accounts, Secrets, Models, Agents, Behavior, Appearance, Advanced and About tabs (`settings_ui.js`), ordered from connections to runtime detail; keys, defaults and per-key semantics are the §7 Default settings table, not this chapter. Accounts holds subscriptions, API providers, custom endpoints, local runtimes and the optional non-loopback network gate; Agents holds task actors and review lanes, whose accounts live in Accounts; Advanced holds process, timeout, local-model, integration, source-control and cleanup controls (worker count is process capacity, so it lives there). Appearance is client-local except Language, the one install-wide choice on that tab: `OUROBOROS_UI_LANGUAGE` (§7), written at once through `POST /api/ui/i18n/language` and never through the Settings draft, beside Import/Export/Regenerate of the translation memory. Models, Available subagents and Review lanes share one grouped source select (`web/modules/route_editor_primitives.js`): the owner picks a source and the editor composes the stored id, so provider prefixes are serialization, never owner input.

Startup & background offers two immediate host checkboxes outside the Settings draft (`settings_autostart.js`): start at sign-in (`GET/POST /api/desktop/autostart`, OS truth) and keep running after the window closes (`GET/POST /api/desktop/background`, the host's `OUROBOROS_DESKTOP_KEEP_RUNNING`); failed writes re-read the actual state. Closing, quitting and Panic in background mode: §9 and DESIGN §9.

The Settings client validates the whole draft before Save and sends no partial save; refresh and failed writes preserve edits, leaving a dirty draft asks first, and the write response distinguishes saved, unsaved and unknown. There is no cross-page draft store and no secret persistence. Skill-requested keys and extension settings sections arrive from the installed-skill list as optional enrichment that lands only on an unchanged draft; catalog updates preserve drafts (`settings.js`, `settings_controls.js`, `settings_catalog.js`).

`settings_secrets.js` owns Show/Hide: saved values come from `POST /api/settings/secret` through the same effective loader as Settings GET, the response is `no-store`, ordinary GET stays masked, and the route adds no settings write or credential probe; it inherits the application's network access, so an intentionally open deployment also allows explicit reveal.

Advanced also hosts the settings sections live extensions register, hydrated before they are shown: the client reads each declarative `form`/`action` component's own `route` with GET and pre-fills exactly the fields a 2xx object names (passwords never), so Save rewrites current values instead of posting first options over them. A `404`/`405` means no current values and the form renders from declared defaults with Save enabled; a transport or server failure renders it with Save disabled, because a blank form must never overwrite values the client could not read.

Each provider card has one compact **Test** action backed by `POST /api/providers/test` (§4): one bounded, physically accounted call (`llm_probe.py`) with none of the chat retry, fallback, tool, reasoning, web, cache or capability-learning paths; draft credentials are request-local and never mutate Settings, the process environment or `LLMClient` caches, and the tooltip discloses that the call may incur provider charges.

Desktop onboarding and the blocking web overlay are the same served `/onboarding` page with the same backend normalization; startup readiness is structural, and completion is the single all-or-nothing `POST /api/onboarding/complete` transaction (§2). Neither a discovery retry nor a reviewer-recovery preview writes settings.

#### Agent accounts

Accounts is the owner-facing projection of Ouroboros's owned Claudexor daemon; the browser never receives the daemon's control token or interprets credentials, and verification distinguishes vendor-live from local-session truth. One `/v2/quota` envelope supplies the windows and typed per-subject absences (`quota`, `quota_absences`), so a missing usage reading stays separate from login truth; only fresh snapshots are eligible for percentages or exhaustion, and a fully-used ratio without a valid future reset does not by itself prove exhaustion. API-key-only adapters gain no fake Login buttons by appearing in a broader execution catalogue. The gateway reads catalog, accounts and quota independently and stamps each facet into the payload's `reads` block, so one refusal never collapses its siblings into a global `unreachable` (§1).

Accounts group into one card per agent family: an aggregate of the accounts rotation can use (signed in and enabled), a "Next up" badge naming who an unpinned run would take (`accountPools`), and the add action. When the engine advertises `get:account-pools` (projected as `unified_accounts`), every account — migrated default logins included, under the reserved `<harness>-default` ids — is a named row with an Enabled toggle and Remove; any other or unreadable engine falls closed to the pseudo-row rendering without Remove or toggle, because a dead button would claim an effect this process cannot have. `verification=not_run` is neutral unknown, and `availability=unknown` re-runs the shared Refresh rather than a new sign-in: an auth probe failure is never proof of logout. Removing a named account keeps the complete deletion receipt — a refusal stays a refusal, and a vendor-owned or left-unchanged disposition becomes a retained-credential warning, not a false sign-out claim.

Connect is link-first and harness-agnostic: a typed disclosure renders the sign-in URL and any one-time code, and typed facts, never prose, select every continuation — `credential_profile_required` plus `add_named_account` selects the name-the-account face, and the exact `terminal_transport_*` code (or `job.nativeCommand.errorCode`) offers the external-terminal continuation (`external_terminal` → `client_pty`; there is no embedded terminal). Only the engine's structural missing-vendor-binary first-create job lets the same owner action consent to one hidden local install through the managed Claudexor CLI and one retry; success requires Claudexor's post-install proof (`installedBinary` plus `installedVersion`), and exit zero without proof is refused. Terminal job state and the account row reconcile, so a stale verification read during login cannot claim failure after the account connected.

Status refresh runs immediately and on visible page or tab activation; hidden pages pay no daemon round-trips, and background polling is read-only and never wakes the daemon — entering Agents is the explicit owner action that restarts an already-provisioned `stale` home, while `not_provisioned`, foreign-owned and repair states stay behind Connect. Job polling is one request at a time with backoff and stops after a bounded run of failures in an honest unconfirmed state, because lost contact proves neither failure nor settlement; a network failure keeps the card and job id, since dropping them could orphan a live server job (`harness_login_cards.js`).

#### Review lanes and Available subagents

Review lanes edit one configuration (§7 Reviewer slots; `reviewer_slots.js`): roster handles or inline API and session channels per row; direct API triad rows also choose Reads the work itself or Packet, while scope and deep review always retrieve. The deep-review block labels a synthesized `OUROBOROS_MODEL_DEEP_SELF_REVIEW` row. Blank models are refused at save; saved choices gone from discovery stay visible as unavailable, never silently changed, and a pin to an account absent from discovery is disclosed only on the word of a facet actually read ("not checked", not "not in discovery"). The standing note states the rule, not live status: review surfaces follow configured rows and wait for subscription capacity rather than silently falling back to API spend. An agent-session row's meta line carries the availability sentence the subagent cards compute (`sessionRouteVerdict`): the row, never the model option, says whether an account can run the selected model.

**Available subagents** is the single task-actor editor: its list-level Enabled flag and at most `MAX_CONFIGURED_SUBAGENTS` stable rows are the saved `OUROBOROS_SUBAGENTS` intent. Each card (anatomy: DESIGN §6) carries one prose field, Description (`recommended_use`), a structured API-model or Agent-session route, optional effort, an optional account pin (empty = compatible-account rotation) and its own `enabled` switch. It is a draft the section's one Save writes, never an instant save; a switched-off card keeps every control editable, and a save that would strand a reviewer reference on it is refused whole, naming the reference. A row is named by its handle — route target plus effective non-default facets, as `codex=gpt-6-astra/xhigh` (`subagent_handle`) — rather than by a stored label, because a label rots once the owner re-points the row; `subagent_id` is a hidden join key, and roster edits never save twin engines. Agent-session rows also select native Access, Full system access (default) or Working files; rows saved without the field default to full for new tasks, and running tasks keep their captured profile. The editor shares only neutral route/model/account/status primitives with Review lanes (`subagents_settings.js`).

Saved intent and live evidence are separate axes: a row's status dot composes intent (saved / draft / generated) with availability and takes the worse tone, and a status, catalog or accounts failure annotates rows, never erases them. Requested and observed model/account stay distinct; historical failure neither disables a row nor ranks alternatives (§6 Route health). A generated default candidate offered by Settings GET is materialized only on Save and never replaces an owner-edited draft. A running task keeps its immutable start snapshot; the save response says changes apply from the next task.

Mutative subagents use Off, Auto and On: explicit values apply to every acting surface, Auto follows runtime mode, and Light allows external work (external workspace, isolated project copy, genesis) — why: §6 Safety and runtime mode; matrix: `ouroboros/config.py`. Read-only children stay available; owner-controlled, from the next task, independent of API versus coding-agent route.

Prompt Cache TTL is one global owner choice (`OUROBOROS_PROMPT_CACHE_TTL`, §7 Default settings) shared by task, review and safety builders, so they cannot drift into conflicting cache horizons; the default favors reuse across long waits and review cycles.

#### Settings save effects

Settings save sorts keys into three effect classes instead of claiming everything became live (membership: `settings_scales.py` `IMMEDIATE_SETTINGS` / `RESTART_REQUIRED_SETTINGS`, applied by `gateway/settings.py`). Hot-apply: total budget, tool timeout, MCP configuration — a failed hot-reconfigure is a save warning. From the next task: models, credentials, reviewer and subagent configuration; a running task keeps its start snapshot, and a failed task-start reload is the chat-visible `task_start_settings_reload_failed` event. Restart-required: `restart_state` on GET and Save compares saved intent with the boot-pinned runtime mode, the bound host and port and the worker-pool startup inputs, never the mutable environment; unknown application facts stay explicit, and a pending mismatch clears only on a confirmed new process or a saved revert, not on sending `/restart` (bind-host provenance: `server_process.py`). A changed skills path or runtime mode also reloads the extension loader at save time, and each pooled worker adopts the server's published extension generation before a task — `worker_process._adopt_published_extensions` → `extension_reconcile_queue.adopt_published_extension_generation`, one bounded reload per generation, events `extension_generation_adopted` and `extension_generation_adoption_failed` emitted there — a bounded attempt, not a convergence guarantee. The local-model manager publishes applied values only after its owned process passes health, and its saved mismatches clear without an Ouroboros restart. In Cyber Pro, Ouroboros configures context, review and Supervisor through the same audited writer, including while a task is active, while Access stays pending until restart; a saved choice never rewrites an existing task snapshot or physical request. Every in-process owner-settings writer holds `settings_document_mutation()` across read, merge and write (§7 Reading and writing the settings document). Absence of a successful status read is never evidence that a runtime is healthy.
